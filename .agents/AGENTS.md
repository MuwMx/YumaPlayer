1. РАЗДЕЛЕНИЕ МОДЕЛЕЙ (Data Layer vs UI Layer)
- Сетевые DTO, сущности БД и UI-стейты (UI State) обязаны быть РАЗНЫМИ data class. 
- Запрещено использовать сетевые аннотации (вроде @SerializedName) в моделях отображения.

2. РЕПОЗИТОРИИ (Repository Pattern)
- Репозиторий отвечает ТОЛЬКО за доставку и кэширование данных (сеть, диск, память).
- Репозиторий возвращает наружу сырые данные или чистые бизнес-модели. Никакого парсинга под UI внутри репозитория.

3. ВЫЧИСЛЕНИЯ И ПАРСИНГ (Utilities)
- Тяжелая обработка строк (Regex, JSON), маппинг и конвертация выносятся в чистые изолированные утилиты (object Parser) без зависимостей от Android Context.

4. VIEWMODEL И UI STATE
- ViewModel управляет только UI-стейтом (StateFlow) и событиями экрана.
- ViewModel не работает с файлами и сетью напрямую — только через вызовы репозиториев.
- ViewModel контролирует потоки, явно переключая тяжелые задачи на Dispatchers.IO.

5. JETPACK COMPOSE (Stateless UI)
- Компоненты Compose должны быть полностью «глупыми» (Stateless). Они принимают готовый State и отдают клики вверх через лямбды (onClick: () -> Unit).
- Внутри Composable-функций запрещена бизнес-логика, расчеты прогресса, вызовы репозиториев и запуск не связанных с UI корутин.

КРИТИЧЕСКИЕ ЗАПРЕТЫ:
- Запрещено прятать Log.d() в методы, возвращающие данные, если это ломает сигнатуру типа (Unit).
- Запрещено лепить монолитные методы «все-в-одном». Если задача комплексная — разделяй её на Интерфейс -> Репозиторий -> ViewModel -> UI.

все по канонам срп, чистоте кода и без костылей
